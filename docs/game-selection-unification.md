# Единые правила игр и дополнений

Проверка 2026-09-09 охватывает потребителей BGG, коллекций, каталога, выбора игры,
создания/редактирования сбора и записи партии во всём репозитории. Причина повторявшихся
ошибок: экраны самостоятельно определяли, можно ли выбрать дополнение, а несколько
проекций сокращали дополнение до ID и названия. Диапазон игроков терялся между
поиском, владением, каталогом и снимком сбора. В формах создания и редактирования
дублировались элементы выбора игроков, оба использовали только диапазон базы.

## Карта потребителей

| Путь | Общий владелец и проверяемое поведение |
| --- | --- |
| Поиск по названию, BGG ID и ссылке | `GamePicker` → `BggSelectionService`; классификация из typed `/thing`, а не метка результата поиска |
| Личная коллекция | Цель `Ownership`: дополнение сохраняется самостоятельно; `LoadOwnershipAsync` проверяет запрошенные ID и официальных родителей |
| Ручное добавление в Club / legacy Camp API | `LoadBaseSelectionAsync` и `BggGameMapper`; выбранные дополнения проверяются одной функцией, метаданные не сокращаются; новый доп объединяется с существующей базой клуба под проверкой ревизии |
| Новый сбор из BGG | Та же базовая игра и набор дополнений; снимок и необязательное владение строятся из одного ответа провайдера |
| Новый сбор из Club / Camp / личной коллекции / вишлиста | `GatheringGameSelectionService` использует общий каталог; только базовые игры; при недоступном BGG использует сохранённые сведения |
| Импорт профиля, legacy Camp и Club; восстановление RollMove | Один BGG загрузчик, `ToImportSelection`, `CampImportSelectionItem.ToSnapshot/ToDraftItem`; тип и все официальные родители сохраняются |
| Обновление метаданных клуба | `BggGameMapper.ToCollectionExpansion`; сохранённое членство дополнений не меняется, известные сведения не стираются неполным ответом |
| Каталоги Club / Camp | `ClubCollectionGame.WithMetadataFallback`, `CollectionItemSnapshot.ToExpansion`; объединение не теряет диапазон уже известного дополнения |
| Фильтр игроков и карточки каталога | `PlayerCountRange.WithExpansions` для фактически присутствующих дополнений; диапазон базы и диапазон с дополнениями показываются отдельно |
| Создание и редактирование сбора | `GatheringGameSnapshot.WithExpansions`, `GatheringRules`; общие `GatheringPlayerLimits` и `ExpansionPicker` |
| Редактирование старого сбора | Только по явному открытию редактирования загружаются отсутствующие диапазоны известных дополнений; при сохранении провайдер вызывается до транзакции, правила повторно проверяются под блокировкой |
| Запись партии / экспорт | Общий `ExpansionPicker`, серверный `GatheringExpansionSelection`; разрешены только дополнения из снимка данного сбора; история и экспорт используют сохранённый снимок |
| Вишлист | Цель `Wish`; дополнение не превращается в желание владеть базой. `GameWishService` сохраняет отдельные правила интереса, владения и наличия коробки |
| Telegram | Отдельного поиска/импорта/выбора игры нет; адаптер открывает Mini App, публикации используют `GatheringPresentationService` и сохранённый снимок |

Цели `BaseGame`, `Ownership`, `Wish` описывают разные действия над одним общим
каталогом. Это не три реализации поиска. В режиме базовой игры поиск дополнения
разрешает его официального родителя и передаёт выбранный ID дополнения дальше.
Если родителей несколько, пользователь выбирает одного. Мутация повторно проверяет
связь по серверным данным. Параметр `allowExpansions=true` сохранён только как
совместимый вариант `mode=item` для ранее загруженных клиентов.

## Диапазон игроков и сохранённые данные

База 2–4 и выбранное дополнение 2–5 дают 2–5. Снятие дополнения возвращает 2–4.
Несколько дополнений расширяют диапазон по минимальной/максимальной границе;
числа игроков не складываются. BGG не описывает все ограничения сочетаний модулей,
поэтому это диапазон по опубликованным сведениям, а не проверка полного текста правил.
Неполный/невалидный диапазон дополнения не расширяет диапазон базы. Для невалидной
базы сохраняется общий резервный диапазон 1–12 с предупреждением.

`ClubCollectionExpansion` получил необязательные `MinPlayers`/`MaxPlayers` без смены
версии документа коллекции. `GatheringGameSnapshot` v4 хранит границы базы отдельно
от диапазона выбранных дополнений; v1–v3 читаются совместимо. На обычном чтении
сохранённые строки не переписываются. Для старого редактируемого сбора восполняются
только отсутствующие сведения известных дополнений с подтверждённым родителем;
названия, идентичность игры, прошлые партии и чужие дополнения не заменяются.
Если BGG недоступен и в старом снимке нет диапазона дополнения, расширять число
игроков на основе догадки нельзя — остаются сохранённые границы.

При выпуске нужно обновить все экземпляры приложения: старый бинарник не понимает
новый снимок v4. SQL-миграций и массового обновления существующих строк не требуется.

Сохранение ручного набора в legacy Camp API выполняется одной локальной транзакцией:
Camp → participant → владение и contributions. Подготовка provider-метаданных находится
вне неё. Владение, доступность коробки и обещание привезти её остаются разными фактами.

## Остальные общие подсистемы

При проходе проверены точки входа Mini App и Telegram и связи с общими сервисами.
Для следующих правил сохраняются существующие владельцы; новые локальные реализации
в рамках исправления не вводились:

| Область | Канонический владелец |
| --- | --- |
| Идентичность и доступ к сообществу | `ParticipantIdentityService`, `CommunityContextResolver`, `ICommunityStore` |
| Административные права | `IAdminAuthorizationService` |
| Владение / доступность / желания | `ParticipantCollectionService`, `GameProviderService`, `GameWishService` |
| Даты, жизненный цикл, вместимость, действия | `CampOperatingWindow`, `CampRules`, `GatheringLifecycle`, `GatheringCapacity`, `GatheringRules`, `GatheringAccessPolicy` |
| Списки и история | `GatheringListQuery`, `ProfileGatheringQuery` |
| Уведомления и отправка | `NotificationService`, `NotificationDispatcher`, `ITelegramGroupMessageSender` |
| Названия, таксономия, BGG URL | `BggGameNameResolver`, `BggTaxonomyCatalog`, `BggGameUrl` |

Разные документы владения, доступности и исторических снимков нужны для разных
жизненных циклов и прав. Унификация означает общие преобразования и правила между
ними, а не слияние пользовательского владения с клубной коллекцией или историей.

## Проверки

- `ProfileCollectionSearchTests`: реальный HTTP-путь поиска и ручного добавления с fake BGG XML; дополнение отдельно, база с отмеченным дополнением, защита вишлиста и родителей.
- `BggSelectionTests`: несколько родителей, отсутствующая обратная ссылка базы, сохранение богатых метаданных, чтение Club/Camp и старых снимков.
- `PlayerCountRangeTests`: создание/редактирование на пятерых, возврат к четырём, запрет вытеснения занятых мест и сохранения пятого места без дополнения.
- `test-data/game-player-ranges.json`: одни примеры для C# и TypeScript — неполные диапазоны, резервное значение, несколько дополнений, выбор/снятие.
- `GamePickerExpansion.test.tsx`, `GatheringExpansionFlow.test.tsx`: выбор из поиска/ссылки, формы создания и редактирования, отправляемые ID и лимиты.
- Полные серверный и клиентский наборы проверяют остальных потребителей. PostgreSQL-сценарии требуют `OYINQ_TEST_POSTGRES`; без него явно пропускаются.

В тестах надёжности уведомлений устранено смешение реального времени с фиксированной
датой сценария: мутация, планирование и диспетчер используют одни тестовые часы.

Фактическая проверка: Release build/restore, `npm ci`, TypeScript check и production
build Mini App прошли; 553 серверных теста прошли без пропусков на отдельном
временном PostgreSQL 18, 136 клиентских тестов прошли. Дополнительные PostgreSQL
сценарии проверяют атомарность ручного набора Camp и добавление дополнения к
существующей игре клуба с проверкой ревизии. Тест сохранности миграций сравнивает
все исходные колонки и их значения, разрешая появление новых колонок при аддитивных
миграциях (раньше добавленные колонки прогресса импорта давали ложное падение).
