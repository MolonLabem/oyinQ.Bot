# Единые правила игр и дополнений

Проверка 2026-09-09 охватывает потребителей BGG, коллекций, каталога, выбора игры,
создания/редактирования сбора и записи партии во всём репозитории. Причина повторявшихся
ошибок: экраны самостоятельно определяли, можно ли выбрать дополнение, а несколько
проекций сокращали дополнение до ID и названия. Диапазон игроков терялся между
поиском, владением, каталогом и снимком сбора. В формах создания и редактирования
дублировались элементы выбора игроков, оба использовали только диапазон базы.

## Карта потребителей

| Путь | Общий владелец и проверяемое поведение |
| --- | --- |
| Поиск по названию, BGG ID и ссылке | `GamePicker` → `BggSelectionService`; классификация из typed `/thing`, а не метка результата поиска |
| Личная коллекция | Цель `Ownership`: дополнение сохраняется самостоятельно; `LoadOwnershipAsync` проверяет запрошенные ID и официальных родителей |
| Ручное добавление в Club / legacy Camp API | `LoadBaseSelectionAsync` и `BggGameMapper`; выбранные дополнения проверяются одной функцией, метаданные не сокращаются; новый доп объединяется с существующей базой клуба под проверкой ревизии |
| Новый сбор из BGG | Та же базовая игра и набор дополнений; снимок и необязательное владение строятся из одного ответа провайдера |
| Новый сбор из Club / Camp / личной коллекции / вишлиста | `GatheringGameSelectionService` использует общий каталог; только базовые игры; при недоступном BGG использует сохранённые сведения |
| Импорт профиля, legacy Camp и Club; восстановление RollMove | Один BGG загрузчик, `ToImportSelection`, `CampImportSelectionItem.ToSnapshot/ToDraftItem`; тип и все официальные родители сохраняются |
| Обновление метаданных клуба | `BggGameMapper.ToCollectionExpansion`; сохранённое членство дополнений не меняется, известные сведения не стираются неполным ответом |
| Каталоги Club / Camp | `ClubCollectionGame.WithMetadataFallback`, `CollectionItemSnapshot.ToExpansion`; объединение не теряет диапазон уже известного дополнения |
| Фильтр игроков и карточки каталога | `PlayerCountRange.WithExpansions` для фактически присутствующих дополнений; диапазон базы и диапазон с дополнениями показываются отдельно |
| Создание и редактирование сбора | `GatheringGameSnapshot.WithExpansions`, `GatheringRules`; общие `GatheringPlayerLimits` и `ExpansionPicker` |
| Редактирование старого сбора | При открытии редактирования загружается полный список официальных дополнений и объединяется с сохранённым; при сохранении новые связи проверяются до транзакции, правила повторно проверяются под блокировкой |
| Запись партии / экспорт | Общий `ExpansionPicker`, серверный `GatheringExpansionSelection`; разрешены только дополнения из снимка данного сбора; история и экспорт используют сохранённый снимок |
| Вишлист | Цель `Wish`; дополнение не превращается в желание владеть базой. `GameWishService` сохраняет отдельные правила интереса, владения и наличия коробки |
| Telegram | Отдельного поиска/импорта/выбора игры нет; адаптер открывает Mini App, публикации используют `GatheringPresentationService` и сохранённый снимок |

Цели `BaseGame`, `Ownership`, `Wish` описывают разные действия над одним общим
каталогом. Это не три реализации поиска. В режиме базовой игры поиск дополнения
разрешает его официального родителя и передаёт выбранный ID дополнения дальше.
Если родителей несколько, пользователь выбирает одного. Мутация повторно проверяет
связь по серверным данным. Параметр `allowExpansions=true` сохранён только как
совместимый вариант `mode=item` для ранее загруженных клиентов.

## Диапазон игроков и сохранённые данные

База 2–4 и выбранное дополнение 2–5 дают 2–5. Снятие дополнения возвращает 2–4.
Несколько дополнений расширяют диапазон по минимальной/максимальной границе;
числа игроков не складываются. BGG не описывает все ограничения сочетаний модулей,
поэтому это диапазон по опубликованным сведениям, а не проверка полного текста правил.
Неполный/невалидный диапазон дополнения не расширяет диапазон базы. Для невалидной
базы сохраняется общий резервный диапазон 1–12 с предупреждением.

`ClubCollectionExpansion` получил необязательные `MinPlayers`/`MaxPlayers` без смены
версии документа коллекции. `GatheringGameSnapshot` v4 хранит границы базы отдельно
от диапазона выбранных дополнений; v1–v3 читаются совместимо. На обычном чтении
сохранённые строки не переписываются. Для старого редактируемого сбора добавляются
официальные дополнения и восполняются отсутствующие сведения с подтверждённым родителем;
названия, идентичность игры, прошлые партии и чужие дополнения не заменяются.
Если BGG недоступен и в старом снимке нет диапазона дополнения, расширять число
игроков на основе догадки нельзя — остаются сохранённые границы.

При выпуске нужно обновить все экземпляры приложения: старый бинарник не понимает
новый снимок v4. SQL-миграций и массового обновления существующих строк не требуется.

Сохранение ручного набора в legacy Camp API выполняется одной локальной транзакцией:
Camp → participant → владение и contributions. Подготовка provider-метаданных находится
вне неё. Владение, доступность коробки и обещание привезти её остаются разными фактами.

## Остальные общие подсистемы

Обновление 2026-09-10: создание и редактирование используют `GatheringExpansionPicker`
поверх общего `ExpansionPicker`: выбор нескольких дополнений, поиск в длинном списке,
возврат к базе и независимые намерения владения/привоза. `AddExpansionToCollectionIds`
и `BringExpansionIds` обязаны быть подмножествами выбранных дополнений. Привоз
подразумевает добавление отсутствующей личной копии, но не владение базовой игрой.
Снятие дополнения из сбора не удаляет глобальную коллекцию или Camp-обещание.
Намерения сбрасываются при снятии выбора и смене базовой игры, отмена формы ничего не пишет.

Сервер готовит только доверенные метаданные до транзакции и использует существующие
`ParticipantCollectionService` / `CampContributionSelectionService` внутри транзакции
сбора. Порядок блокировок редактирования: community → Camp → participant → gathering.
Сохраняются проверки организатора, рабочего интервала/регистрации, вместимости,
публикации и уведомления об изменении. Исторические партии не переписываются.
Отсутствующие массивы новых полей сохраняют поведение старых клиентов; новые формы
всегда передают массивы, поэтому флаги базовой игры относятся только к базе.
Официальные ссылки дополнений остаются доступны даже при сбое обогащения BGG;
при полном сбое используются ранее сохранённые связи, новые произвольные ID не принимаются.

Регрессии: `GatheringOwnershipCreationTests` (несколько дополнений, создание → изменение
→ снятие), `GatheringGameSelectionServiceTests` (старые снимки, новые связи и сбои),
`BoardGameGeekClientTests` (сбой метаданных не скрывает список),
`GatheringExpansionFlow.test.tsx` (отправляемые намерения обеих форм),
`PostgreSqlStabilizationTests.EditingExpansionsRollsBackSelectionOwnershipAndBringingTogether`
(атомарность на PostgreSQL, запускается в CI).

При проходе проверены точки входа Mini App и Telegram и связи с общими сервисами.
Для следующих правил сохраняются существующие владельцы; новые локальные реализации
в рамках исправления не вводились:

| Область | Канонический владелец |
| --- | --- |
| Идентичность и доступ к сообществу | `ParticipantIdentityService`, `CommunityContextResolver`, `ICommunityStore` |
| Административные права | `IAdminAuthorizationService` |
| Владение / доступность / желания | `ParticipantCollectionService`, `GameProviderService`, `GameWishService` |
| Даты, жизненный цикл, вместимость, действия | `CampOperatingWindow`, `CampRules`, `GatheringLifecycle`, `GatheringCapacity`, `GatheringRules`, `GatheringAccessPolicy` |
| Списки и история | `GatheringListQuery`, `ProfileGatheringQuery` |
| Уведомления и отправка | `NotificationService`, `NotificationDispatcher`, `ITelegramGroupMessageSender` |
| Названия, таксономия, BGG URL | `BggGameNameResolver`, `BggTaxonomyCatalog`, `BggGameUrl` |

Разные документы владения, доступности и исторических снимков нужны для разных
жизненных циклов и прав. Унификация означает общие преобразования и правила между
ними, а не слияние пользовательского владения с клубной коллекцией или историей.

## Проверки

Выбор нескольких дополнений и явное добавление в личную коллекцию используют один путь в Club и Camp, при создании и редактировании. Только обещание привезти на кэмп зависит от режима. `GatheringOwnershipCreationTests` проверяет Club для каталога и BGG: обнаружение новых дополнений, отдельное владение, сохранность клубной коллекции и отсутствие Camp-вкладов. `GatheringExpansionFlow.test.tsx` проверяет обе формы в обоих режимах, включая снятие отметок и подсказки.

- `ProfileCollectionSearchTests`: реальный HTTP-путь поиска и ручного добавления с fake BGG XML; дополнение отдельно, база с отмеченным дополнением, защита вишлиста и родителей.
- `BggSelectionTests`: несколько родителей, отсутствующая обратная ссылка базы, сохранение богатых метаданных, чтение Club/Camp и старых снимков.
- `PlayerCountRangeTests`: создание/редактирование на пятерых, возврат к четырём, запрет вытеснения занятых мест и сохранения пятого места без дополнения.
- `test-data/game-player-ranges.json`: одни примеры для C# и TypeScript — неполные диапазоны, резервное значение, несколько дополнений, выбор/снятие.
- `GamePickerExpansion.test.tsx`, `GatheringExpansionFlow.test.tsx`: выбор из поиска/ссылки, формы создания и редактирования, отправляемые ID и лимиты.
- Полные серверный и клиентский наборы проверяют остальных потребителей. PostgreSQL-сценарии требуют `OYINQ_TEST_POSTGRES`; без него явно пропускаются.

В тестах надёжности уведомлений устранено смешение реального времени с фиксированной
датой сценария: мутация, планирование и диспетчер используют одни тестовые часы.

Фактическая проверка: Release build/restore, `npm ci`, TypeScript check и production
build Mini App прошли; 553 серверных теста прошли без пропусков на отдельном
временном PostgreSQL 18, 136 клиентских тестов прошли. Дополнительные PostgreSQL
сценарии проверяют атомарность ручного набора Camp и добавление дополнения к
существующей игре клуба с проверкой ревизии. Тест сохранности миграций сравнивает
все исходные колонки и их значения, разрешая появление новых колонок при аддитивных
миграциях (раньше добавленные колонки прогресса импорта давали ложное падение).

Создание сбора кэмпа показывает явную отметку «Я привезу» и для своей игры из сохранённого каталога, включая режим без BGG. Владение само по себе не включает эту отметку. Выбор проходит существующие серверные проверки регистрации, даты, владения базой и выбранными дополнениями; GameProviderService остаётся владельцем статуса коробки. GatheringOwnedGame.test.tsx проверяет отправку обеих явных опций без повторного добавления игры в коллекцию.


## Сложность BGG

`statistics/ratings/averageweight` читается в существующем Thing-запросе вместе
с остальными метаданными. Значения вне 1–5, пустые и некорректные значения дают
`null`. Необязательный `boardgameweight` обрабатывается защитно: выбирается
ответ с наибольшим количеством голосов, при равенстве — ближайший к среднему,
затем более лёгкий. Без голосов среднее округляется до ближайшего уровня BGG
(половина вверх). Это приблизительный запасной вариант, а не результат опроса.
Доступность опроса в живом API в этой среде не подтверждена; тест опроса использует
явно синтетическую XML-фикстуру. Дополнительных запросов нет.

Среднее и уровень проходят через `ExternalGame` → `BggGameMapper` → снимки
импорта/личной коллекции/Club/Camp/вишлиста → снимок сбора. Повторный импорт и
обновление метаданных записывают новые сведения; история сборов не переписывается.
Это необязательные поля существующих JSON-форматов: старые версии читаются без
миграции, неизвестная сложность не получает бейдж. Русские подписи и CSS-классы
в БД не сохраняются: их добавляет только HTTP-проекция либо Telegram-представление.

Общий `ComplexityBadge` используется в каталоге (включая вложенные дополнения),
вишлисте, локальных результатах поиска, выбранной игре при создании сбора,
личной коллекции, превью импорта, управлении коллекцией и карточках сборов.
`ComplexityDetails` дополнительно показывает среднее с максимум двумя знаками.
Текстовые публикации Telegram используют ту же серверную классификацию и
существующее ограничение подписи 1024 символа. Необогащённые результаты BGG
search не имеют сложности: Thing по-прежнему загружается только после выбора.
Компактный календарь профиля и Telegram-клавиатуры остаются без дополнительных
тегов. Проверка браузером выполняется на фиктивных данных без live BGG/Telegram.

### Connected planning

Creation from catalog details uses the same picker and server selection. Copying uses an organizer-owned, same-community immutable gathering snapshot; selecting another game drops the copy source. Aggregate demand may select a saved wish snapshot from the same community without merging other participants' wishes into the ordinary catalog. Both paths preserve official expansion membership and reuse player limits, mutation checks and transactional notification planning. Details: [Connected planning](connected-planning.md).

### Лимиты игроков при выборе дополнений

Когда выбранное дополнение увеличивает допустимый максимум, общий `fitPlayerLimits` выставляет «Максимум» и «Оптимально» на новый предел. Это применяется при создании (включая заранее выбранные дополнения) и редактировании Club/Camp. После выбора организатор может изменить значения вручную. Удаление дополнения ограничивает значения оставшимся диапазоном; сервер по-прежнему запрещает уменьшать вместимость ниже занятого состава. Сохранённые снимки и общий контракт `test-data/game-player-ranges.json` используют диапазоны официально выбранных дополнений, без суммирования их максимумов.

### Сохранённый BGG-аккаунт профиля

`CampBggImportCoordinator.GetProfileSourceAsync` возвращает аккаунт и дату последнего подтверждённого глобального импорта участника (`CampId = null`). Источником остаются существующие сохранённые задания; истечение черновика, неудачная попытка сменить аккаунт и очистка браузерного хранилища не сбрасывают подтверждённый аккаунт. Scoped Camp-импорты не заменяют глобальный источник.

`GET /profile/collection/imports/source` доступен только владельцу через проверенную Telegram-идентичность и не требует выбранного сообщества. `POST /profile/collection/imports` без `bggInput` повторно использует этот аккаунт и обычную очередь; явный `bggInput` запускает импорт другого аккаунта. В профиле доступны «Обновить из BGG» и «Сменить аккаунт». Применение коллекции по-прежнему требует подтверждения выбранных игр и не удаляет ранее сохранённое владение. Новый аккаунт становится сохранённым после подтверждения. Автоматическое расписание обновлений не включено.


## Загрузка всех дополнений BGG в сборе (2026-09-15)

Обнаружение уже входит в `IBoardGameGeekClient.GetGameDetailsAsync`: отдельный клиент,
поиск или таблица игр не нужны. В XML Thing базовой игры ссылки
`type="boardgameexpansion"` без `inbound` (или с `inbound="false"`) ведут к дополнениям.
У самого дополнения `inbound="true"` ведёт к родителям. Проверены реальные сохранённые
XML-ответы: Coup (131357), Brass (28720), Scythe: The Wind Gambit (223555) в
[fixtures клиента boardgamegeek](https://github.com/lcosmin/boardgamegeek/tree/develop/test/xml).
Родитель не обязательно является базой: существующий typed выбор проверяет тип отдельно.

Клиент исключает повторные/неположительные ID, ссылку на себя, другие типы связей,
а после обогащения — неподходящий тип элемента и противоречащих родителей.
Обогащение использует существующий парсер, авторизацию и повторы, пакетами не более 20 ID.
Ошибка пакета сохраняет ссылки и успешные результаты остальных пакетов;
`ExpansionLookupIncomplete` сообщает интерфейсу о неполных метаданных.
Полные результаты хранятся 30 минут в уже зарегистрированном memory cache;
ошибки и неполные результаты не кэшируются, чтобы повтор загрузки мог восстановить данные.

`useGatheringExpansions` используется формами создания и редактирования независимо
от источника базы: каталог Club/Camp, личная коллекция, BGG, желание и копия сбора.
Он объединяет ответ с сохранёнными дополнениями и не изменяет выбранные ID.
Есть состояния загрузки, пустого списка и русская кнопка повтора; ошибка не блокирует форму.
Старое прикреплённое дополнение остаётся доступным, даже если BGG перестал его возвращать.
Новые ID при сохранении желания/копии проверяются тем же сервисом; сохранённый набор
можно повторить без провайдера. Параметры и выбор в текущей форме переживают её обновления.

Просмотр и выбор не создают владение, GameCopy или Camp-вклад. Базовый импорт по-прежнему
использует `excludesubtype=boardgameexpansion` и проверяет typed Thing; отдельный
существующий импорт явно принадлежащих дополнений сохраняется.
Только существующие явные отметки «Есть у меня» / «Я привезу» изменяют владение.
`ClubCollectionExpansion` получил необязательные URL миниатюры и изображения, которые
передаются из существующего BGG snapshot. Старые JSON читаются без этих полей;
SQL-схема и миграции не меняются.
