# Удаление профиля

Профиль → Настройки → «Удалить мой профиль» доступен без сообщества и регистрации. Команда `/deleteprofile` в личном чате открывает те же настройки, а не отдельный Telegram-сценарий удаления. Подтверждение предупреждает об удалении во всех сообществах и невозможности восстановления.

`DELETE /api/miniapp/profile` требует подписанный Telegram initData и `{ "confirmed": true }`. Идентичность берётся только из подписи; идентификаторы в query/body не выбирают другого участника. Операция идемпотентна и выполняется в одной транзакции.

Удаляются профильные имя и контакты, личная коллекция, хотелки, все Camp registrations/days/custom answers/quotes, вклады и настройки видимости, запросы на привоз, настройки и личная очередь уведомлений, сохранённые административные разрешения и собственные временные выборы Telegram. Telegram ID автора кэмпа и выданных другим администраторам разрешений заменяется служебным `0`: сами кэмпы и чужие разрешения сохраняются, но старый owner bootstrap больше не привязывается к удалённому пользователю. Личные BGG imports остаются только как отменённые служебные идентификаторы: username, draft, confirmation и error очищаются, lease инвалидируется. Ссылки на внешние партии, добавленные пользователем, удаляются.

Будущие организованные сборы отменяются через `GatheringRules.Cancel`; запись участника снимается через `WithdrawParticipant` с продвижением очереди. Уведомления об отмене/освободившемся месте сохраняются для других участников в этой же транзакции. Состояние и результаты прошлых партий сохраняются, профильные/локальные/записанные имена и имена в legacy audit обезличиваются. Новые публикации используют «Удалённый профиль» без Telegram-ссылки. Ранее отправленные сообщения, скачанные файлы и резервные копии не обещается удалять автоматически.

Исторический `Participant` остаётся как анонимная FK-идентичность: `DeletedAt`, имя «Удалённый профиль», отрицательный служебный `TelegramUserId = -Id`, пустые контакт/предпочтительное имя/активное сообщество/private-chat capability. Отдельная `DeletedProfile` хранит только исходный Telegram ID и дату выбора. Автоматическое создание/обновление профиля и личные сообщения не снимают opt-out. Обычные Mini App endpoints отвечают `410 profile_deleted`, приложение размонтирует прежние экраны и очищает свои browser storage keys.

`POST /api/miniapp/profile/recreate` с явным подтверждением удаляет opt-out и создаёт новый `Participant`, с новым Id/PublicId, пустыми коллекцией и регистрациями. Старая анонимная история не привязывается. Mini App initData не подтверждает возможность отправки личных сообщений: новый профиль снова требует `/start` для private-chat capability.

`ParticipantOperationLock` — PostgreSQL session advisory lock по Telegram-идентичности, удерживаемый на открытом EF connection через endpoint-owned транзакции. Используется также identity service, Telegram adapter, gathering creation и notification dispatcher. Удаление ждёт ранее начатую собственную операцию/доставку; новые запросы ждут удаления и получают opt-out. Camp/сборы/участник блокируются в существующем порядке, а `ParticipantWriteStore` проверяет актуальное `DeletedAt` под row lock для владельцев коллекции и регистрации. BGG worker пишет прогресс и результат через условное обновление собственного lease, поэтому отмена/удаление не позволяет позднему ответу вернуть личные данные. Клиент игнорирует запоздалые `410` предыдущего поколения после явно подтверждённого создания нового профиля.

Миграция `20261003073652_ProfileDeletion` добавляет nullable `Participant.DeletedAt` и opt-out table; существующие участники остаются активными. Миграции завершаются перед HTTP/workers. Upgrade-тесты заполняют старую схему SQL, затем применяют текущие миграции дважды.

Проверки: реальные authenticated routes с подменой target/query, отказ без подтверждения, idempotent delete, 410 для старых сессий, новая пустая идентичность; PostgreSQL erasure через несколько сообществ с сохранением других участников, очереди и результатов, миграция заполненной схемы, сериализация уже открытой операции, импорт между последним чтением и записью результата, начатая доставка уведомления; frontend confirmation/error/retry/double-submit, размонтирование навигации/читателей, поздний ответ после recreation. Browser-проверка охватывает светлую/тёмную темы на ширине 320/390/1440, отмену подтверждения, ошибку и повтор удаления, открытие старой сессии и явное создание нового профиля.
