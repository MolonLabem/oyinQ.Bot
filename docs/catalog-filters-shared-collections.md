## Применимость и семантика

| Условие | Club | Camp |
| --- | --- | --- |
| Поиск по игре / дополнению | Да | Да |
| Число игроков | Да | Да |
| Год выпуска: от / до | Да | Да |
| Типы (любой выбранный) | Да | Да |
| Категории (все выбранные) | Да | Да |
| Коллекция клуба / есть у меня / мой вишлист | Да | Да |
| Игры участников и конкретные участники | Нет | Да |
| Доступность: точно привезут / нужно договориться | Нет | Да |
| Уже / ещё не запланированы | Да | Да |
| Сортировка: название / игроки / сыгранные партии | Да, вне счётчика | Да, вне счётчика |

Club-only условий нет. Механики в старом каталоге не фильтровались; новая панель
не добавляет неподдерживаемый фильтр. Диапазон игроков сохраняет правила
`PlayerCountRange.WithExpansions`; неизвестный диапазон не совпадает с числом.
Выбранные владельцы объединяются через OR. Категории и типы сохраняют прежние
AND/OR правила. Поиск и сортировка меняют список непосредственно.

В группе «Игроки» выпадающие списки «От» / «До». `fromPlayers` и `toPlayers`
задают включительный интервал: игра подходит, если поддерживает хотя бы одно
число в нём. Одна пропущенная граница открыта; одинаковые границы дают точное
число. Ноль, отрицательные и обратный интервал отклоняются для списка и подсчёта.
При изменении одной границы в интерфейсе пересечённая вторая сдвигается вместе с ней.
Режим `supported` (по умолчанию) использует `PlayerCountRange.WithExpansions` с
дополнениями эффективной коллекции; `best` — пересечение с сохранённым `BestPlayers`.
Неизвестный базовый диапазон не превращается в запасные 1–12 мест при поиске.
Карточка и детали различают «Базовая игра: 1–4» и «С дополнениями: 1–6»;
это возможности доступной коробки, а не вместимость уже созданного сбора.

`filters.playerCounts` формируется сервером из полного авторизованного
эффективного каталога до поиска и фильтров: объединение известных диапазонов
с доступными дополнениями и сохранённых рекомендаций. Список отсортирован,
без повторов и выдуманных промежутков между раздельными диапазонами. Нет данных —
списки отключены. Пагинация и пустой результат не меняют варианты. Выбранные границы
сохраняются, даже если обновление источника убрало соответствующее число.
`BggBestPlayerRecommendation.Ranges` читает целые положительные числа,
включительные диапазоны с `–`, `-` или `—` и их сочетания через запятую;
ошибка в любой части исключает всю рекомендацию. Один разбор обслуживает поиск
и варианты списков. Формат BGG и сохранённые снимки не меняются.
Обе границы дают одну группу и один чип. Без границ режим не ограничивает каталог.
Старый API-параметр `players` работает как точное число, если новых границ нет;
новые границы имеют приоритет. Старые записи sessionStorage с `players`
восстанавливаются в обе границы с прежним режимом (`supported` по умолчанию).

Год выпуска использует только `YearPublished`: `fromYear` и `toYear` включительны,
пропущенная граница открыта, обе пропущенные отключают критерий. Неизвестный год
не совпадает при активной границе. Допустимы целые годы 1–9999 (границы записи года,
без зависимости от текущего года); `fromYear > toYear` возвращает validation.
Панель сохраняет ошибочный ввод для исправления, блокирует подсчёт и применение.
Обе границы дают одну группу и один чип; удаление чипа очищает обе.
Новые параметры проходят `catalogFilters` → `buildCatalogQuery` → `/catalog` →
`CatalogQuery` → `GameCatalogService.Matches` одинаково для списка и `countOnly`.

## Интерфейс и состояние

Карточки каталога показывают обложку, название, число игроков, тип и сохранённую
сложность справа вверху; нажатие на всю карточку открывает экран игры.
Сводка доступности и число запланированных сборов приходят с сервера и находятся
в одной строке без отдельного блока «Подробнее». Дополнения остаются внутри
карточки базовой игры, а оформление их списка применяется только к каталогу,
не к личной коллекции. Club и Camp используют те же карточки со своими сводками
доступности; критерии фильтрации и состояния кэмпа не выводятся из оформления.

Каталог показывает по 10, 20 или 50 карточек; размер страницы сохраняется в
sessionStorage. Пагинация выполняется над полным ответом после группировки:
дополнения остаются с базовой игрой, самостоятельные дополнения получают свою
карточку. Стрелки и выбор номера страницы переводят фокус к началу результатов.
Поиск, фильтры и сортировка сбрасывают страницу; возврат из игры её сохраняет.
После уменьшения коллекции номер ограничивается последней доступной страницей.
Сложность в каталоге, фильтрах и остальных экранах использует общий
`ComplexityBadge` и серверные подписи/классы с цветами для обеих тем.

Общая панель на native `dialog`: снизу на телефоне, по центру на desktop.
Браузер обеспечивает modal focus/inert и Escape; закрытие возвращает фокус.
Telegram Back и нажатие на фон отменяют черновик. Body фиксируется на время
панели; прокручивается только содержимое, footer с действиями остаётся доступен.
Поля используют существующие темы, safe area и viewport-переменные.

Разделы находятся на одном уровне и сворачиваются независимо. При более шести
вариантах поиск доступен сразу при открытии раздела; список имеет ограниченную
высоту и собственную прокрутку. Поиск игнорирует регистр и различие «е»/«ё».
Порядок задаёт сервер, выбор его не переставляет. Все выбранные значения доступны
для удаления внутри раздела, даже если скрыты поиском; краткий заголовок показывает
количество. Над каталогом чипы занимают одну горизонтальную строку, независимо
от числа выбранных значений. Число подходящих игр показано в кнопке применения.

Открытие копирует applied → draft. «Сбросить» внутри меняет draft; «Показать»
применяет его. Наружный сброс и удаление чипа сразу обновляют applied.
Счётчик — число активных групп, без поиска и сортировки. Хранение: sessionStorage
`oyinq-catalog-filters-v1:<mode>:<communityKey>`. Неизвестные значения и больше
не существующие варианты отбрасываются; другой key/mode монтирует отдельное
состояние. Существующие ключи приложения не меняются.

`GET /catalog?...&countOnly=true` проходит прежнюю авторизацию и общий отбор,
но возвращает только `{total}`. Дополнения, показанные внутри базовой карточки,
не считаются второй карточкой. Предпросмотр не скачивает каталог, не строит
карточки и не загружает историю партий. Запрос откладывается на 300 мс;
AbortController и идентичность параметров исключают устаревший результат.
При ошибке подсчёта можно повторить или применить без числа. Ошибка списка
показывается отдельно от нуля, сохраняет выбор и предлагает повторить.

## Источник и карта потребителей

| Путь | Владелец / изменение |
| --- | --- |
| Каталог, детали, вишлист, создание сбора | `GameCatalogService.LoadAsync` читает авторитетный источник |
| Camp каталог, провайдеры на дату, сборы | `EffectiveCampCatalogService` → `SharedCollectionReader`, отдельно вклады |
| Camp регистрация, подсказки базовых игр | `CampEndpoints` читает тот же источник |
| Legacy Camp BGG импорт | worker проверяет базовое членство через тот же reader |
| Club просмотр / JSON экспорт / статистика размера | актуальное содержимое reader; редактируемость — backend `CanEdit` |
| Ручные изменения / JSON замена / BGG импорт | текущая транзакция источника и `ReplaceCollection`; читатели видят после commit |
| Обновление метаданных / служебный refresh | исходные клубы; linked Club нельзя изменить локально |
| Профиль, Camp Available/Bringing, вишлисты | собственные таблицы, синхронизация их не изменяет |
| Уже созданные сборы / Telegram публикации / история | сохранённый снимок, без переписывания при изменении источника |

Кэмпы используют существующий SourceClubId, включая активные и архивные.
Связь кэмпа по-прежнему выбирается только в Draft. `BaseCollectionJson`
остаётся fallback для кэмпа без связи; его не требуется перезаписывать.

Миграция `20260916104537_SharedClubCollections` добавляет nullable
`Clubs.SourceClubId`, индекс и FK Restrict. Старые независимые копии получают
null, их происхождение не угадывается. Действие «Подключить коллекцию» сохраняет
явную связь, авторизуя оба клуба прежним серверным механизмом. Связанный клуб
предоставляет содержимое своим участникам, но не права на исходное сообщество.
Локальные записи не удаляются; мутации общей коллекции отклоняются на backend
и UI показывает read-only. Цепочки разрешены, циклы запрещены; изменения связей
сериализуются PostgreSQL advisory lock, в том числе между экземплярами приложения.
Удалённый soft-delete источник сохраняет последнюю коллекцию для своих связей.

Изменения содержимого читаются при каждом запросе из БД: нет фонового копирования,
очереди синхронизации или process-local кэша. Импорт BGG по-прежнему добавляет /
обновляет выбранные записи, не трактует отсутствие игры как удаление. JSON-замена
валидируется и сохраняется одним документом. Неуспешная/ожидающая загрузка не
публикует пустую коллекцию. Удаление из источника снимает только унаследованное
членство; игра с локальным вкладом, владением или желанием остаётся в нужной
проекции. Наличие в коллекции источника не даёт Camp статуса «точно привезут».

## Свежесть

Ответы каталога помечаются `no-store`; список, варианты и число строятся заново.
Новый авторизованный запрос после commit видит новую коллекцию на любом экземпляре.
Открытый Mini App перечитывает каталог при возврате на экран/из деталей, при
focus/visibility и событии локального успешного изменения. В постоянно открытом
неактивируемом каталоге изменения другого пользователя появятся после следующего
такого события или применения фильтра. Push и WebSockets не используются. Исключение:
пока запрошенные оценки BGG загружаются, видимый каталог перечитывается раз в пять
секунд; после завершения или ошибки загрузки этот опрос прекращается.

При неизменных community/search/sort/applied filters фоновая загрузка и её ошибка
сохраняют смонтированный `CatalogGameList`, ключи карточек и раскрытые дополнения.
Статус обновления и возможность повторить запрос показываются отдельно. Раньше
`state.loading` заменял весь список на `Loading`: высота страницы уменьшалась,
браузер ограничивал scrollY и возврат после Alt+Tab перескакивал к началу.
`Page` прокручивает вверх только при смене заголовка; ключ сообщества не зависит
от ответа. Защита версий запросов в `useAsync` и проверка `data.params === params`
сохранены. При изменении запроса прежние результаты не показываются.

## Ручная приёмка

1. На 320, 360, 390, 430 px и desktop открыть каталог и панель в светлой/тёмной теме.
   Проверить длинные подписи, прокрутку, закреплённую кнопку и экранную клавиатуру.
2. Найти и выбрать шестую категорию, изменить поиск, удалить выбор по чипу.
   Свернуть и открыть раздел; выбор и поиск сохраняются, порядок не меняется.
3. Изменить черновик, закрыть Escape/фон/Telegram Back, открыть снова. Затем
   применить, проверить число, индикатор загрузки, сброс внутри/снаружи и нулевой ответ.
4. Быстро менять фильтры и сообщества при медленной сети, затем отключить сеть:
   старый ответ не должен подменять текущий; ошибку можно повторить без потери выбора.
5. У источника добавить, изменить, удалить игру вручную и импортом; проверить
   два связных клуба и кэмпа, варианты фильтров, число и выбор игры для нового сбора.
6. Удалить исходную игру с локальным Bringing, желанием и существующим сбором:
   локальные записи и история сохраняются. Без Bringing коробка не подтверждена.
7. Проверить администратора только потребителя: чтение разрешено, изменение
   источника запрещено. Независимые клубы и старые копии не меняются.
8. Перейти на последнюю страницу, изменить размер, искать игру с другой страницы.
   Открыть игру/дополнение и вернуться; страница сохраняется. Обновление уменьшенной
   коллекции не оставляет пустую страницу. Проверить все пять цветов сложности.

## Рейтинг, популярность и карточки · 12.11.2026

Сортировки: `rating` (по умолчанию, средняя оценка BGG по убыванию), `popular`
(число прошедших неотменённых сборов данного сообщества, достигших MinimumPlayers)
и `name`. Организатор, подтверждённые участники и гости учитываются через
`GatheringCapacity.MinimumReached`; очередь не считается. Факт записанной партии
не нужен для популярности. `RecordedPlays`, история и BG Stats по-прежнему требуют
подтверждения партии. При равном рейтинге используется популярность, затем имя/ID;
без оценки игры идут в конце. На первоначальной загрузке оценок порядок временно
определяется популярностью/именем, чтобы каждая полученная порция не переставляла список.

`BggCatalogRatingService` читает отдельный кэш публичных оценок PostgreSQL,
добавленный миграцией `20261112044952_BggRatingCache`. Авторизованное чтение каталога
ставит в очередь только нужные BGG ID; `countOnly` не загружает оценки. Worker
обрабатывает до 20 ID за запрос `thing?stats=1`, вне транзакции. Lease и условное
завершение по токену защищают несколько экземпляров и поздние ответы. Успешная
оценка живёт сутки; ошибка даёт паузу 15 минут и сохраняет прежнее значение.
Повтор после истечения срока требует нового чтения каталога. Явные нулевые голоса
означают отсутствие оценки; отсутствующая/повреждённая статистика — ошибку, а не
команду стереть прежнюю оценку. Без настроенного BGG используются сохранённые данные.
Таблица не хранит владение, членство или локальные названия и не меняет снимки игр.

Карточки показывают игроков, длительность и оценку компактными SVG-значками с
доступными текстовыми подписями. Тип игры остаётся в деталях. Базовая вместимость и
диапазон с доступными дополнениями показаны отдельно. Неизвестная длительность
опускается: оценка длительности для расписания не подставляется в справочные данные.
Миграцию и worker проверяют интеграции на изолированном PostgreSQL с поддельным BGG;
перед rollout на production применяются обычные проверки миграций и резервного копирования.
