# Планирование, доставка уведомлений и сыгранные партии

## Архитектура

`CommunityTime` переводит ввод времени сообщества в UTC; `CampOperatingWindow` проверяет начало включительно и окончание исключительно. `CampRules` сохраняет правила календарных дней регистрации. Дата регистрации сама по себе не разрешает сбор после закрытия кэмпа.

`NotificationService` сохраняет намерение с уникальным семантическим ключом. Изменение сбора, повышение из очереди, изменение регистрации, отмена сообщества и уведомление о несостоявшемся сборе сохраняются вместе в транзакции. Доставка Telegram выполняется после коммита. Ошибка Telegram не откатывает участие. Уведомление о готовом черновике импорта фиксируется вместе с завершением задания.

`GameProviderService` использует `GameCatalogService` / `EffectiveCampCatalogService`. `ClubProvided` означает коробку в базе клуба/кэмпа; `ConfirmedParticipantProvider` — явное Bringing; `AvailableParticipantProviders` — только возможных поставщиков; `NoKnownProvider` — отсутствие подтверждения и кандидатов. Для конкретного сбора кэмпа учитывается выбранная дата регистрации. «Я привезу» вызывает существующий сервис Camp-вкладов, не меняет владение и не распространяется на другие кэмпы.

`GatheringDashboardService` строит обзоры из `GatheringListQuery`, `ProfileGatheringQuery`, канонической вместимости и обеспечения коробки. Личный обзор API сохранён для совместимости; в профиле расписание доступно в «Календаре», без отдельного блока «Что дальше». Обзор организатора показывает его сборы; эффективный администратор видит всё выбранное сообщество. Выводятся недобор, полный сбор с очередью, неподтверждённая коробка, ближайшие два часа, отмены за двое суток, ошибки публикации и существенные ошибки доставки. Camp-агрегаты для администратора: сегодняшние регистрации и игры Bringing/только Available. Обзоры ограничены выборками по 200 строк и сообщают об усечении; полное расписание остаётся в календаре/списке.

Каталог и подбор игры используют общий `GameCatalogService.LoadAsync`. Club — база плюс личные игры исключительно текущего пользователя; Camp — база плюс явные вклады зарегистрированных участников. Фильтры: владелец, подтверждённое/возможное наличие, запланировано/не запланировано, игроки, типы и категории. «Популярные» сортируются по числу явно подтверждённых партий в сообществе; рядом показано число будущих сборов. Completed не увеличивает число партий.

## Миграции

1. `20260904072034_PersistentParticipantCollection` — предыдущий этап: глобальное владение, безопасное заполнение из Camp-вкладов, приватный запуск бота, глобальные задания импорта.
2. `20260904080727_CampOperatingInstants` — добавляет StartsAtUtc/EndsAtUtc, конвертирует прежние StartDate 00:00 и **EndDate + 1 день 00:00** через часовой пояс связанного сообщества, затем удаляет прежние колонки. Производные DateOnly-свойства остаются только для регистрации. Не двигает сборы и не сокращает окно.
3. `20260904081750_NotificationDelivery` — очередь, предпочтения, состояние блокировки Telegram. Не создаёт ни уведомлений, ни включённых напоминаний существующим участникам.
4. `20260904084352_GatheringPlayRecords` — отдельные записи партий и фактические игроки; случайные стабильные PublicId участников и гостей. История посещаемости не заполняется предположениями. Внешние ключи защищают записи от удаления связанной истории.

5. `20260904092743_PlayOutcomesReferencesAndReleases` — отдельный исход сбора, ссылки партий с авторами, выпуски и состояние их доставки. Старые отрицательные записи переносятся в исход с полным аудиторским снимком `LegacyPlayOutcomeJson`; положительные партии и их игроки сохраняются. Прежняя одиночная ссылка сохраняется как служебный архивный столбец; ссылки подходящего официального хоста переносятся в новые строки.

Миграции предназначены для применения вперёд. До production сравнить данные и выполнить SQL на копии PostgreSQL. Локальные EF InMemory-тесты не проверяют блокировки и конкурентное выполнение PostgreSQL.

## Доставка и настройки

Состояния: Pending, Delivering (аренда отправки), Delivered, Failed, SuppressedByPreference, CannotMessageUser, DeliveryUnknown, Expired. Хранятся число попыток, последнее время, категория ошибки и Telegram message ID при успехе. Текст нужен для отложенной доставки; стеки исключений и токены в очереди не сохраняются.

Worker выбирает строку через `FOR UPDATE SKIP LOCKED`. Явные временные отказы повторяются с увеличением задержки, максимум пять попыток. Успех не отправляется повторно. Если ответ потерян или процесс погиб после начала отправки, результат неизвестен: **автоматического повтора нет**, поскольку Telegram sendMessage не предоставляет ключ идемпотентности. Это предотвращает слепую повторную отправку, но не гарантирует доставку такого сообщения. Организатор видит проблему и может связаться с участником.

Отсутствие PrivateChatStartedAt и блокировка бота фиксируются как невозможность DM. Настоящее приватное сообщение обновляет способность доставки и разрешает повтор; одна лишь авторизация Mini App этого не делает. Запись на сбор доступна и до приватного запуска, с понятным приглашением запустить бота.

| Категория | По умолчанию | Отключаемая |
|---|---|---|
| Повышение из очереди, перенос времени, отмена, несостоявшийся сбор; сбой темы публикаций у администратора | Включено | Нет |
| Изменение описания/условий | Включено | Да |
| Выход участника, замена из очереди, недобор у организатора | Включено | Да |
| Полный сбор | Выключено | Да |
| Нет подтверждённой коробки у организатора | Выключено | Да |
| Готов черновик BGG-импорта | Включено | Да |
| Напоминание | Выключено | Да: 30/60/120/360/720/1440 минут |

Одна настройка напоминаний применяется к организатору и подтверждённому игроку. Очередь ожидания не получает напоминаний. Перед отправкой повторно проверяются актуальные время, статус, участие и настройка. Перенос до отправки сдвигает момент доставки; после доставленного напоминания новый экземпляр не создаётся, перенос сообщается отдельным обязательным уведомлением. Полный сбор сообщает каждому получателю максимум один раз, даже после освобождения и повторного занятия мест. Предупреждение организатору о коробке появляется не ранее чем за два часа и не повторяется для того же сбора.

## Возможное пересечение

`Gatherings:ScheduleConflictWarningWindowMinutes` = 120, допустимо 0–1440. Проверяется близость времени начала в UTC, без выдуманной длительности BGG. Учитываются будущие активные сборы, которые участник организует или где подтверждён; не очередь и не отменённые/завершённые.

Ответ 409 с `code=gathering_schedule_conflict` содержит сборы. После явного подтверждения Mini App повторяет исходную операцию с `confirmScheduleConflict=true`. Доступ, собственность организатора, Camp-регистрация, вместимость и точные границы проверяются заново.

## Запись партии и BG Stats

Completed — только состояние расписания. Организатор завершённого сбора отвечает «Да, сыграли» или «Нет, не состоялась». Ответ «Нет» сохраняет исход, автора, время и ревизию на сборе; записи партии нет. Уже подтверждённую партию нельзя превратить в отрицательный исход: API возвращает 409 `play_outcome_conflict`. Тот же код защищает от устаревшей ревизии. Автоматического подтверждения и голосования нет.

Для «Да» организатор уточняет фактическое окончание, необязательную длительность, игроков из состава сбора и использованные дополнения. Явные NoShow/CancelledInAdvance не выбраны по умолчанию, но организатор может исправить состав. История посещаемости и снимок исходного сбора остаются неизменными. В сыгранной истории пользователя отображаются только партии, где он указан фактическим игроком; статистика тоже считает только подтверждённые партии.

[Официальный контракт BG Stats](https://www.bgstatsapp.com/support/push-plays-to-bg-stats-from-other-apps-or-websites/) проверен 4 сентября 2026 года. Адаптер формирует `https://app.bgstatsapp.com/createPlay.html?data=...`: sourceName, стабильный sourcePlayId, UTC-время фактического окончания, игра с BGG ID, игроки со случайными устойчивыми UUID, необязательная длительность и место. Дополнения передаются в комментарии, поскольку отдельного поля в контракте нет. Telegram ID, внутренние числовые ключи, username и контакты не передаются.

Доступны ссылка, системный share и копирование. Файлы OyinQ/BG Stats, резервные копии и загрузка файлов не поддерживаются. В OyinQ можно работать без установленного BG Stats. Имя игрока входит в ссылку, о чём UI предупреждает. BG Stats показывает подтверждение импорта; включённая пользователем автопубликация может отправить партию в BGG.

Каждая внешняя ссылка — отдельная `GatheringExternalPlayReference` с автором. Добавлять могут организатор и люди из фактического состава подтверждённой партии, удалять — автор или организатор. Очередь и исключённые из фактического состава пользователи доступа не получают. Принимается только HTTPS на точном хосте `app.bgstatsapp.com`, без userinfo, управляющих символов и нестандартного порта, до 2048 символов. Сервер ссылку не скачивает. Уникальность — партия плюс нормализованный URL.

## Другие приложения

- [Board Record, официальное руководство](https://board-record.com/): документирует импорт BG Stats JSON и BGG/BGA, но не описывает совместимый createPlay-контракт. Генерация чужого резервного формата и прямой адаптер не добавлены.
- ScorePal: найден [исторический блог разработчика](https://medium.com/@scorepal/version-2-3-a86bcbb8b738), но актуальный поддерживаемый контракт ввода партии не подтверждён. Одноимённый спортивный сервис не принят за документацию настольного трекера. Адаптер не добавлен.

## Ручная проверка

1. На копии PostgreSQL сохранить количество участников, регистраций, вкладов Bringing, сборов и посещаемости. Применить миграции, сверить числа/снимки и уникальность публичных ID. Для старого кэмпа проверить последнюю минуту старого EndDate и полночь следующего дня. Повторный старт не создаёт записей и рассылок.
2. Создать кэмп 10 сентября 09:00 — 13 сентября 09:00 в Asia/Almaty. 08:59 первого дня запрещено, 09:00 разрешено, 08:59 последнего разрешено, 09:00 запрещено — и через UI, и подменой API. Последняя дата присутствует в регистрации с «до 09:00». Проверить редактирование и автоматическое закрытие ровно в конце; в Europe/Berlin проверить несуществующее/двойное локальное время.
3. Свежий пользователь открывает сбор без /start, получает Participant и может записаться в клуб. CTA открывает runtime-бота и возвращает к тому же сбору. После реального приватного сообщения CTA пропадает. Заблокировать бота, вызвать важное уведомление, проверить CannotMessageUser и восстановление после нового приватного сообщения.
4. Выключить необязательное сообщение между постановкой и доставкой: отправки нет. Отмена и повышение из очереди остаются обязательными. Включить полный сбор, заполнить, освободить и заполнить снова: нет повторной лавины. Проверить явный 429/5xx, 403, потерю ответа и перезапуск worker. Неизвестный исход не повторяется автоматически.
5. Включить напоминание за час: оно не приходит раньше, приходит в пределах интервала worker (обычно до 15 секунд), не повторяется после рестарта. Перенести сбор перед отправкой, отменить сбор, выйти из него, выключить настройку — проверить актуальные правила. Очередь ожидания не получает напоминаний.
6. Создать/вступить/перенести сбор в пределах ±120 минут от другого: виден мягкий запрос. Подтвердить и проверить успех; тот же флаг не обходит Camp-регистрацию, чужое управление и закрытый сбор.
7. Собственная игра без Camp-вклада не появляется как Bringing. Available показывает только возможность, «Я привезу» создаёт/обновляет один вклад текущего кэмпа. На другой день без регистрации поставщик не считается доступным. Несколько провайдеров не дублируются, чужая личная коллекция не раскрывается клубу.
8. Проверить обзор обычного организатора и эффективного администратора, недобор, очередь, публикацию/доставку с ошибкой, сегодняшние Camp-агрегаты. Календарь должен вести в правильное сообщество. Сравнить фильтры каталога и подбор игры; Completed без подтверждения не увеличивает число партий.
9. Дождаться Completed: партии ещё нет. Подтвердить «Да», убрать одного человека и дополнение, задать окончание. Проверить отдельную запись, неизменённую историю и отсутствие выдуманных NoShow. Чужой пользователь/очередь не может редактировать; два одновременных редактора получают конфликт ревизий. Для ещё неподтверждённого сбора «Нет» сохраняет только исход. Для уже подтверждённой партии «Нет» возвращает конфликт и ничего не удаляет.
10. Открыть BG Stats на тестовом телефоне: проверить подтверждение, имена, BGG ID, UTC-окончание, длительность и дополнения в комментарии. Два участника получают одинаковый sourcePlayId. В данных ссылки отсутствуют Telegram ID/контакты. Проверить без установленного BG Stats, системный share и копирование.
11. Добавить ссылку https://app.bgstatsapp.com/; второй фактический игрок видит её. Проверить несколько авторов, дубликат, удаление автором и модерацию организатором. javascript:, data:, file:, http:, относительный URL и userinfo отклоняются. Посторонний и исключённый из фактического состава не могут добавлять ссылки или получать ссылку импорта.
12. На Telegram iOS/Android/Desktop проверить светлую/тёмную темы, ширину 320–390 px, поля date-time, вкладки профиля, длинные имена и ссылку экспорта. Проверить новые `profileImport`-ссылки и старые Camp `tab=mine&import=...`.

Живые PostgreSQL-конкуренция, доставка Telegram и импорт на устройстве требуют этих проверок; сборки и моки их не заменяют. Массовая просьба владельцам привезти коробку, файлохранилище и неподтверждённые адаптеры других трекеров не добавлялись.

13. Суперадминистратор открывает «Обновление OyinQ». Предпросмотр ничего не отправляет. Отметить два управляемых сообщества, проверить тему, текст и runtime-кнопку. Подтвердить, обновить результат доставки. Повторить ошибочные: успешный чат не получает второе сообщение. Перезапустить worker, проверить отсутствие повторов. Удалённый получатель виден только в отчёте и не отправляется. При неопределённом результате проверить чат вручную.
14. Внешняя игра: выбрать BGG-результат с дополнениями. Без флажков личная коллекция не меняется; с флажком добавляется база и выбранные дополнения, повтор не создаёт дубликатов. В кэмпе отдельный флажок создаёт Bringing только этого кэмпа. На копии PostgreSQL вызвать сбой последнего сохранения: личное владение, вклады и сбор откатываются вместе; Telegram до коммита не вызывается.
