# Единый профиль и личная коллекция

## Структура

Профиль содержит «Игры», «Хотелки», «Календарь», «Настройки». Нижняя навигация сохранена. Личная коллекция глобальная и доступна без сообщества; хотелки показываются только для выбранного сообщества. В Camp личный режим переиспользует карточки, детали, исходящие просьбы и добавление из `CampWishBrowser`, без переключателя общего спроса и списка участников. Club использует прежний `WishlistPanel`.

Управление своей коробкой из хотелки или профиля участника открывает единый профиль внутри приложения. Исходный экран остаётся смонтированным, «Назад» восстанавливает его и прокрутку. Вкладка профиля, поиск и фильтр коллекции сохраняются отдельно по контексту. При смене сообщества Camp-состояние перемонтируется с новым ключом; ответы прежнего контекста не используются.

`CampProfileProvider` получает настройки из `CampWishlistService.SettingsAsync`: действующие согласия, свои дни, свои отказы и идентификаторы собственных востребованных игр. Это проекция существующих данных, не отдельное хранилище. Единственный редактор согласий — `CampPrivacy` над содержимым вкладок «Игры» и «Хотелки». Checkbox показывает только серверное значение, блокируется при сохранении/перечитывании; ошибка видима. Общие хотелки показывают состояние и ссылку на этот редактор. Публикация не включается при открытии или переносе интерфейса.

## Коллекция и привоз

Над коллекцией: количество, «Добавить», поиск; в Camp — фильтры «Все», «Точно привезу», «Могу привезти». Подсказка о спросе фильтрует тот же список. Входящие просьбы раскрываются компактным блоком; ответ отказом возможен и после удаления владения. Подтверждение ведёт к статусу собственной коробки в коллекции.

Карточка показывает обложку, название, краткие характеристики и видимый выбор статуса. `CampBoxControl` сохраняет отсутствие предложения, Available, Bringing и отдельный отказ. Отказ/снятие отказа идут через существующий сервис просьб, обещание — через `CampContributionSelectionService`. «Удалить из коллекции» находится в меню «Ещё», с подтверждением и прежним серверным запретом удаления активной коробки. Дополнения остаются под базовой игрой и имеют собственные отметки и даты.

Новая отметка действует на все дни регистрации владельца. Для старой отметки смена Available/Bringing **не меняет даты**. Исключения находятся в «Другие дни»; видна строка «Только …», а при пустом пересечении — предупреждение об отсутствии доступных дней. В регистрации объясняется влияние изменения дней на привоз.

Контракт собственного списка вкладов различает:

- `AllAttendanceDays`: сохранённый режим (`AvailableDates == null` в базе).
- `SelectedDates`: исходное явное ограничение, включая даты, удалённые из регистрации.
- `AvailableDates` в DTO: текущее пересечение с днями регистрации, как и раньше.

PUT commitment без параметров дат сохраняет старый режим; `allAttendanceDays: true` явно возвращает все дни участия; `availableDates: [...]` задаёт проверенное исключение. Одновременная передача обоих режимов отвергается. Модель EF и схема не изменились: новая миграция не нужна. Старые массивы никогда не преобразуются в null по совпадению наборов дат. Каталог, хотелки, просьбы, профиль и сборы продолжают использовать канонический `EffectiveDates`.

## Добавление и импорт

Форма добавления изначально закрыта. Скрытие сохраняет поиск GamePicker, выбранную игру и дополнения; незавершённый выбор виден с действием продолжить. Импорт открывается отдельным компактным действием внутри формы. Поддерживаются прежние `profileImport`, `import` и storage-ключи, выбор импортированных игр, повтор после ошибки и серверный фоновый job.

Закрытие импорта сохраняет его ID и выбор, показывает статус с «Открыть» и не вызывает cancel. Ошибка импорта тоже остаётся доступной для повторного запуска. При скрытом импорте прежний polling приостанавливается; открытие перечитывает состояние. Скрытые страницы импорта не прокручивают коллекцию при смене стадии. Общий success-event обновляет настройки, список вкладов, хотелки и коллекцию; GET ничего не рассылает.

## Ручной сценарий

1. A и B зарегистрированы на Camp, у B два дня участия из четырёх. A добавляет хотелку, B владеет игрой, но не публикует коллекцию.
2. B открывает профиль: видимость над играми, форма добавления закрыта; подсказка спроса приводит к коробке. «Точно привезу» сохраняется без календаря. A видит коробку только на два дня B и может открыть существующий сбор.
3. B выбирает «Другие дни», оставляет один день. Смена статуса и повторный вход сохраняют исключение. Возврат «Все дни моего участия» явно снимает его. После изменения регистрации меняются только коробки с этим режимом.
4. A просит другую видимую коробку. B отвечает из блока входящих просьб; отказ остаётся отдельным статусом. A видит результат в своих хотелках. Приватность не меняет обещаний, старые скрытые хотелки остаются без имени.
5. B сворачивает начатый импорт, видит статус, возвращается к сохранённому выбору. Закрытие не отменяет job. В Club и без сообщества доступны глобальные игры, без элементов привоза.
