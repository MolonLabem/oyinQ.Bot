# Обновление существующей базы

При обычном запуске `Program.cs` ожидает `Database.MigrateAsync()` до запуска HTTP-сервера, Telegram и всех hosted workers. В журнал выводятся ожидающие миграции и сообщение об их завершении. Ошибка не перехватывается: приложение не начинает обслуживать запросы с неподготовленной схемой. EF хранит применённые версии в `__EFMigrationsHistory`; повторный запуск не повторяет уже завершённые преобразования. Это не одна транзакция на весь выпуск: после сбоя ранее завершённые миграции могут оставаться применёнными.

## Что происходит со старыми данными

| Данные | Поведение обновления |
|---|---|
| Участники, Telegram ID, выбранное имя и контекст | Сохраняются; для внешних ссылок создаётся отдельный случайный `PublicId`. |
| Личные игры из старых Camp-вкладов | Копируются в глобальную коллекцию по участнику + BGG ID + типу. При дублях приоритет у ручного источника, затем у свежего снимка. Исходные вклады и обязательства остаются. |
| Клубный каталог и базовые снимки кэмпов | Сохраняются без подмены содержимым файлов репозитория. Обновление приложения не импортирует новые игры. |
| Регистрации, дни, город, проживание | Сохраняются в прежнем кэмпе. Владение играми не добавляет обязательство их привезти. |
| Даты кэмпов | Старое начало становится локальной полуночью, конец — локальной полуночью после прежней последней даты; обе границы хранятся в UTC. Кэмпы без дат остаются без дат. |
| Сборы, снимки игр, участие, гости и время | Сохраняются. `Completed` не превращается автоматически в подтверждённую партию. |
| Старые Camp-импорты | Сохраняют `CampId`, состояние, черновик и результат. Новые профильные задания используют `CampId = null`. |
| Уже существующие записи партий промежуточной версии | Явный исход переносится в сбор. Отрицательная запись и её состав сохраняются в `LegacyPlayOutcomeJson`; положительные записи остаются партиями. Допустимые старые BG Stats URL переносятся в ссылки с автором; исходная колонка сохраняется. |
| Уведомления и запуск бота | Исторические сообщения не восстанавливаются догадкой. `PrivateChatStartedAt` остаётся `null`, пока не придёт настоящее приватное сообщение; прежним пользователям может снова понадобиться запустить бота. Обновление не создаёт рассылку выпуска. |

Перенос ownership использует только существующие положительные BGG ID и сохранённые снимки, без запросов к BGG. Игры, удалённые из старой базы до выпуска, восстановить этим переносом нельзя. Отсутствующий BGG ID не угадывается.

## Порядок выпуска

1. Уточнить фактическую версию в `__EFMigrationsHistory`. Эти миграции продолжают цепочку `20260901073247_CleanBaseline`; база с другой, дорефакторинговой схемой требует отдельного плана переноса. Не заменять её пустой baseline и не исправлять таблицу истории вручную.
2. Проверить восстановление резервной копии production в отдельную базу. На ней выполнить миграции именно выпускаемого артефакта. Для исходников задать `Database__ConnectionString` на копию и выполнить `dotnet ef database update --project oyinQ.Bot.csproj --configuration Release`. Эта команда не запускает Telegram или фоновые обработчики. Секрет подключения не записывать в документацию или Git.
3. Сверить данные до и после: число и содержимое участников, регистраций и дней, Camp-вкладов/commitments, клубных и базовых JSON, сборов/участия/гостей и заданий импорта. Убедиться, что каждая уникальная положительная BGG-идентичность прежнего вклада присутствует в личной коллекции, а даты кэмпа преобразованы в его часовом поясе. Проверить список миграций и повторить `database update`: новых изменений быть не должно.
4. На время реального перехода остановить **все старые экземпляры и workers**, сделать актуальную резервную копию и запустить новый экземпляр. Этот выпуск нельзя накатывать с одновременной работой старого и нового кода: миграция дат удаляет прежние колонки `StartDate`/`EndDate`. Блокировка EF защищает выполнение миграций, но не делает старый код совместимым с новой схемой.
5. Дождаться сообщения о завершении миграций и успешной готовности приложения. Проверить профиль старого пользователя, его коллекцию, регистрацию, обязательства и историю. Только затем масштабировать новый экземпляр. Не запускать старый образ на новой схеме для отката: миграции направлены вперёд; восстановление резервной копии требует остановки записей и учёта изменений после выпуска.

## Автоматическая проверка

`PostgreSqlStabilizationTests.MigrationsBackfillPersonalOwnershipWithoutLosingCampCommitmentsOrRegistration` создаёт настоящую базу на версии `20260903073138_AddGatheringGuests`, заполняет старые таблицы, применяет весь выпуск дважды и сравнивает все прежние колонки сохранённых строк, включая JSON, временные метки и внешние ключи. Дополнительно проверяет дедупликацию ownership, точные UTC-границы, новые PublicId, отсутствие выдуманных партий и рассылок, неизвестную DM-возможность и отсутствие ожидающих миграций.

Запускать с `OYINQ_TEST_POSTGRES`, указывающим на отдельный локальный тестовый PostgreSQL с правом создавать базы. Тест создаёт и удаляет только собственную базу `oyinq_test_<guid>`. Без этой переменной PostgreSQL-тесты пропускаются; такой запуск не доказывает перенос данных.

Проверка выполнена на PostgreSQL 18.4. Это проверка представительных старых данных, а не фактической production-копии: её репетиция остаётся обязательным шагом выпуска.
