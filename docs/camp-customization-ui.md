# Camp customization and UI audit (2026-10-03)

Camp creation and editing share `CampConfigurationEditor`; participant registration and already-registered views share `CampInformation`, `CampRegistrationFields` and `CampQuote`. `CampConfigurationRules` owns normalization, answer validation, itemized pricing and saved-quote preservation. The Mini App sends choices, never an authoritative total.

## Consumer map

| Consumer | Contract and verification |
| --- | --- |
| Admin creation / editing / overview | Versioned configuration, shared sections, exact local dates and timezone; questions and option IDs persist through save/read/edit. Creation validates configuration and local times before consuming the Telegram selection ticket. |
| Registration gate / profile settings | Description, HTTPS map link, payment instructions, custom questions and quote. Details remain accessible after registration. Required answers participate in canonical registration completeness. |
| Camp catalog, wishlist, providers, gathering participation | Existing `CampParticipationPolicy` checks also validate required custom answers; no separate client-only registration gate. |
| Own registration GET / PUT / quote POST | Current community membership required; answers and saved quotes belong to the authenticated participant. Supplied participant IDs or totals do not delegate ownership or change server prices. Quote POST is read-only and accepts incomplete required answers for a live preview. |
| Authorized admin roster | Question labels and presented answers, plus each participant's saved amount and currency. Existing scoped admin authorization still protects every read/export/send. |
| Human CSV / XLSX / Telegram roster | Dynamic question columns and saved total/currency. XLSX amounts are numeric; answers remain text. CSV guards formula-leading text. Telegram keeps bounded messages and offers files when an answer is too long. |
| Technical CSV snapshot | Appends `registration_data` and `camp_configuration`, preserving existing column order and saved JSON. |
| Camp create / edit, gathering create / edit, played-party end | `DateTimeField` uses `DateInput` plus explicit 00–23 hours / 00–59 minutes on every device. Existing community timezone, Camp interval and DST rejection rules remain server authority. |

## Pricing and answers

Configuration v1 supports description (6000 characters), location name (200), HTTPS location URL (1000), payment instructions (2000), optional pricing and at most 20 custom questions. Questions support short text, multiline text, one choice from 2–32 options, and checkboxes; each can be required. A required checkbox must be checked. Short text answers allow 400 characters and multiline answers 2000. IDs are stable and independent of labels. URLs and text render as escaped React content, never HTML.

Pricing supports KZT, RUB, USD, EUR, KGS and UZS, amounts from 0 to 10,000,000 with up to two fractional digits, optional daily base price, optional early price, housing surcharge, choice surcharges and checkbox surcharges. Housing and question surcharges may be daily. Daily quantities count selected attendance dates, including partial opening/closing dates. One-time quantities are one. Early price applies to registrations on or before the specified date in the Camp timezone, including that entire day. This is a registration deadline; payment instructions may describe the organizer's separate payment process. The app does not verify transfers or record paid status.

Saving snapshots the currency, total, line quantities/unit prices and calculation time. Changes to name or city preserve the saved quote even after the early deadline or an organizer's price update. Changes to selected dates, housing or normalized custom answers recalculate using current tariffs. The preview uses the same saved-quote preservation rule as PUT. An older client omitting answers preserves the participant's existing answers; it cannot bypass required questions for a new registration. Failed writes retain entered choices; stale preview responses cannot replace the current amount.

After the first registration, existing question definitions/options/surcharges and their order are immutable under the Camp row lock. New optional questions can be appended; required questions cannot be introduced for already-registered participants. Existing answers, completeness and quotes survive this append unchanged. Camp description, location, payment instructions and base pricing remain editable; edits never rewrite other participants' saved answers or amounts. The existing one-active-community-binding-per-Telegram-group model is unchanged. This feature configures individual Camps, not a recurring-event series or automatic reuse of archived registrations.

The referenced Halloween sheet uses name/contact, games brought, collection link, wishes, hourly arrival choice, costume choice and a comment. No extra input type or enforced capacity was present in the sheet. Questions use the same generic editor for every event; there are no event-specific shortcuts. Collections and wishes retain their existing canonical sections.

The pricing editor uses visible amount/unit fields and optional early price/date fields. It reuses `CampPriceInformation` for the participant-facing preview and `CampRegistrationFields`/`CampQuote` for a configurable itemized example. The authenticated admin `/camps/pricing-preview` endpoint normalizes unsaved configuration and calls `CampConfigurationRules.Quote`; it does not persist data or trust supplied totals. Preview controls are optional, debounce edits and discard obsolete responses. `FullscreenButton` is shared by community, global profile and administration headers, including Camp creation.

## UI principles and audit scope

Audited all screen modules under `MiniApp/src/pages` and their shared controls. They use the same Telegram light/dark tokens, typography, primary/ghost/danger actions, semantic badges, page headings, fields, error notices, loading/retry states, navigation and responsive surfaces. Broad catalogs/rosters retain their browsing width; forms and detail views use a narrower reading width. Responsive overrides serve these different purposes without introducing separate palettes.

The Camp admin form was the principal inconsistency: a dense flat card and a browser-controlled time input. Creation uses shared `FormSection` surfaces for group, name/dates, event information, pricing, questions, collection and review. Question editors expand individually. Mobile review labels wrap without squeezing values into a narrow column. Date and time consumers share themed controls; the current policy is recorded on 2026-11-11 below.

Browser verification covers creation, registration, gathering creation, gathering list, game catalog, profile settings and admin roster at 320, 390, 768 and 1440 pixels in light/dark themes, with en-US browser locale and Pacific/Honolulu browser timezone. Assertions check viewport overflow, containment of visible controls, color scheme, absence of AM/PM/native datetime-local inputs, and exact local-time creation payloads. The browser uses bounded representative API fixtures; automated route/domain/PostgreSQL tests separately verify real validation, authorization and persistence. Native Telegram peer selection and device-specific iOS/Android date dialogs still require device testing.

## Regional dates and times — 2026-11-06 (superseded)

The earlier 24-hour UI policy above is historical. The Mini App now follows the first supported `navigator.languages`/`navigator.language` preference, independently of the Russian UI language. Native picker appearance is controlled by the browser/OS; JavaScript cannot read every custom OS regional override. Invalid, unsupported or missing preferences use Russian day-first formatting, with a deterministic DD.MM.YYYY text fallback and explicit 24-hour controls when a system picker cannot be used. API dates remain YYYY-MM-DD and wall times YYYY-MM-DDTHH:mm. Native controls retain minute precision and exact bounds; invalid fallback dates cannot retain a previously accepted canonical value.

Structured Mini App dates use the shared formatter, including community-local schedule grouping, attendance/registration dates, history, review screens and conflict messages. The internal `currentLocalMinute` formatter retains `h23` for ISO comparisons. Telegram, server-rendered messages, exports and older responses containing only formatted text keep their existing day-first/24-hour fallback; they do not have device regional preferences. No server localization, database migration or timezone change is needed.

Verification: 325 Mini App tests pass, including US/GB/Russian preferences, absent/malformed/unsupported locales, a regional hour-cycle extension, midnight, community timezone/DST boundaries, leap-day validation, invalid partial edits and date limits. TypeScript, Vite production build and Docker build pass (temporary Dockerfile adds the environment CA only to dependency-download steps). The .NET suite passes 827 tests with PostgreSQL and zero skips; a rebuild also passes 17 changelog/release tests. Chromium checks cover 24 combinations of US/GB/Russian/missing regional preferences, 320/390/768 px and both themes, with exact wall-time submissions from a Honolulu device timezone and no overflow or page errors. Browser locale emulation verifies JavaScript formatting and input locale attributes; native picker chrome still follows the host/browser and requires physical Telegram WebView testing for device-specific appearance.

## Day-first dates everywhere — 2026-11-11

The 6 November change still selected month-first dates for `en-US`, and native date/datetime-local controls could ignore the input's `lang` in a Telegram WebView. The current policy is deterministic day-first presentation: numeric dates are DD.MM.YYYY, named dates put the day before the month, and times use 00–23 hours. All display consumers use `dateTimeFormatter`; `DateInput` and `DateTimeField` own every editable date. No browser-controlled date/time input remains.

Consumer audit: Camp creation/editing and review; gathering creation/editing and played-game end time; pricing deadlines and price previews; catalog day filters; registration and box attendance dates; wishlist dates; gathering lists, details, dashboards and conflict messages; profile calendar and played history; import/admin timestamps and roster dates. Telegram messages, notifications and human-readable CSV/XLSX already use day-first presentation. Technical CSV, ICS, BG Stats, API values, imports and saved snapshots retain their documented ISO/UTC contracts.

Date editing keeps real-calendar, required, disabled and inclusive-bound validation. Incomplete or impossible dates clear the submitted value; finishing a date edit preserves the chosen time. Camp boundary days still clamp to their exact operating minutes. Numeric keyboards can enter 06112026 as 06.11.2026. Existing ISO values reopen without changing the day, time or timezone.

Manual checks: use US browser/OS settings, then British and Russian settings. Create and reopen an ambiguous date such as 07.08.2026; verify the payload is 2026-08-07 and that changing the browser timezone does not shift local wall values. Check 29.02.2024, reject 29.02.2026 and 12.31.2026, clear required fields, edit a partial date, and exercise both Camp boundary minutes. Repeat on a narrow light/dark screen and physical Telegram iOS/Android WebViews.

Verification: the prepared Git-index export passed TypeScript, 332 Mini App tests, the Vite production build, 827 .NET tests (including 52 PostgreSQL integrity tests, zero skips), embedded release-input validation and the Docker build. Chromium exercised the real shared controls in 18 combinations of US/GB/Russian locale, 320/390/768 px and light/dark theme from a Honolulu device timezone: exact ISO submissions, numeric typing, partial edits, bounds and no overflow/page errors. API responses in those browser checks were fixtures; physical Telegram WebView testing remains a separate device check.

## Migration and regressions

`20261003063649_CampCustomization` adds two non-null JSONB columns with empty version-1 defaults. It does not alter registration dates, housing, city, collection or gathering data. A populated previous-schema database is migrated twice, reopened, and checked for intact registration eligibility and persisted Unicode configuration/answers/quote. Existing visibility migration tests seed the current model then restore their historical schema, explicitly restoring the historical visibility flags before upgrading.

Regression coverage includes inclusive early-price cutoff in a non-UTC timezone; daily and option/housing amounts; malformed fields/URLs/money; required/unknown answers; read-only previews and forged totals; private-response authorization; save/read/edit and saved-price preservation; locked questions; roster/CSV/XLSX/Telegram serialization; formula-safe answers; stale previews; and exact shared local-time input including midnight and Camp bounds.
