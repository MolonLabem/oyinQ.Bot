# Версии коллекций и атомарное обновление BGG

`CollectionRevision` — версия опубликованного содержимого исходного клуба.
Одна эффективная операция увеличивает её на один; одинаковое содержимое оставляет
ревизию и `UpdatedAt` прежними. Прогресс задания не является версией коллекции.
Исторические значения, включая 617, сохраняются. Раньше worker вызывал
`ReplaceCollection` для каждой игры, поэтому одно обновление сотен игр создавало
сотни версий.

## Владелец правила и карта потребителей

`Club.ReplaceCollection` проверяет документ и использует
`ClubCollectionSerializer.ContentEquals`. Сравнение типизированное: старые документы
нормализуются до v2, порядок JSON-свойств и расположение игр/дополнений не влияют
на результат. Пустые необязательные массивы таксономии нормализуются. Порядок
метаданных таксономии сохраняется как часть представления. При no-op исходный JSON
не переписывается. Валидация и проверка ожидаемой ревизии предшествуют no-op.

| Потребитель | Поведение |
| --- | --- |
| `ClubCollectionService.AddOrReplaceGameAsync`, `RemoveGameAsync`, `ReplaceAsync` | Блокировка актуальной строки, проверка expectedRevision, одна публикация либо no-op. Удаление отсутствующей игры ничего не меняет. |
| `ClubEndpoints`, панель администратора | Существующие POST/DELETE/PUT и серверная scoped-авторизация; устаревшая ревизия даёт конфликт даже для предполагаемого no-op. |
| `ClubBggImportService` | Готовый импорт публикуется через тот же ReplaceCollection; повтор идентичного импорта не меняет версию. |
| `ClubCollectionRefreshGenerator`, служебное восстановление | Тот же ReplaceCollection вместо прямого присваивания документа и счётчика. |
| `ClubMetadataRefreshService` | Staging и progress отдельно; один ReplaceCollection только в финальной транзакции. |
| Экспорт/JSON-восстановление | Экспорт только читает; имя файла содержит эффективную версию. Восстановление того же документа — no-op. |
| `SharedCollectionReader`, `GameCatalogService`, `EffectiveCampCatalogService` | Читают актуальный источник на запрос, без межзапросного кэша или отдельного механизма синхронизации. Незавершённый staging не виден. |
| Каталог, создание сбора, профиль, Telegram, provider/wish-проекции | Используют общие каталоги. Владение и Camp Bringing не выводятся из наличия игры у клуба. Снимки существующих сборов не переписываются. |
| DTO `ClubCollectionState` | У linked Club возвращает содержимое, revision и UpdatedAt канонического источника, плюс sourceClubId и canEdit=false. Идентичность версии — источник + ревизия. |
| Admin overview / `CopyFromClubAsync` | Собственная ревизия Club остаётся токеном конкурентного изменения связи. Реальная смена SourceClubId увеличивает её; повтор той же связи — no-op. Это не эффективная версия документа linked Club. |
| EF defaults / создание сообщества / исторические миграции | Начальная версия 1 сохраняется; исторические значения не пересчитываются. |

Другие поля `revision` (например, подтверждение партии) относятся к своим сущностям
и не изменены. Новый кэш или принудительное downstream-invalidation не добавлялись.

## Staging, транзакции и восстановление

Задание фиксирует BGG ID игр на старте. Worker забирает очередной шаг под существующей
арендой, загружает типизированные данные BGG вне транзакции и сохраняет результат
в jsonb `StagedCollectionJson`. Документ использует существующий сериализатор
коллекции, а не raw JSON провайдера. Токен аренды проверяется перед каждым сохранением;
старый worker после перехвата аренды не может применить результат. Повторное
использование DbContext не переиспользует ранее отслеживаемый прогресс.

После последнего результата одна транзакция:

1. Проверяет полноту staging и действующую аренду.
2. Блокирует и перечитывает текущий исходный Club.
3. Обогащает только оставшиеся игры, сохраняя их текущий набор дополнений.
4. Оставляет новые игры без staging нетронутыми и не возвращает удалённые.
5. Сравнивает, публикует изменившийся документ один раз и завершает задание.

`UpdatedGames` показывает число реально изменившихся игр. Ноль означает «Данные уже
актуальны». Даже ошибка сохранения последнего шага откатывает всю публикацию.
При ошибке BGG задание становится Failed, уже сохранённый staging остаётся для
диагностики, live-документ не меняется этим заданием. Явный повтор создаёт новое
задание, как прежде. Прерывание процесса оставляет аренду; после её истечения
работа продолжается с сохранённого шага. Параллельные самостоятельные изменения
администраторов не откатываются при ошибке задания.

## Добавление и изменение игры

Верхняя кнопка «+ Добавить игру» открывает `ClubGameSheet` с общими `GamePicker`
и `ExpansionPicker`. Технические операции находятся в свёрнутом блоке. Сохранение
закрывает панель, обновляет данные и показывает результат; новая игра видна через
поиск по её названию. Escape, фон, кнопка закрытия и Telegram Back закрывают панель.
Во время отправки повторное сохранение и закрытие заблокированы.

Для существующей игры отображаются «Уже в коллекции» и «Сохранить изменения».
POST принимает точный итоговый набор expansionBggIds: снятые дополнения удаляются,
новые проходят существующий `BggSelectionService`, проекция — `BggGameMapper`.
Уже сохранённые дополнения можно оставить/убрать при недоступном BGG. Новые данные
требуют доступного провайдера. Неизменённый набор отключает сохранение; серверный
no-op также идемпотентен. Ревизия черновика фиксируется при открытии панели;
фоновая перезагрузка страницы не заменяет её. После конфликта доступна явная
загрузка актуальной коллекции с новым выбором игры.

## Миграция и проверка

`20260916114347_AtomicClubMetadataRefresh` добавляет только nullable
`StagedCollectionJson` (jsonb) и `UpdatedGames` (integer) в существующее задание.
Старые завершённые задания остаются читаемыми. Незавершённое задание без staging
перезапускает загрузку с первого ID, сохраняя уже опубликованную старым кодом
коллекцию и её ревизию. При выпуске нужно остановить старые workers перед запуском
новых: старый бинарник всё ещё умеет публиковать по одной игре. Frontend и backend
выпускаются вместе из-за точной семантики выбора дополнений в POST.

Регрессии: три игры 10→11 с неизменными live-данными на 1/3 и 2/3; идентичное
повторение; ошибка провайдера и финального сохранения; перехваченная аренда;
два workers с повторно используемым контекстом; A/B→A/C и изменение дополнений;
linked Camp/Club; обычные мутации, импорт и no-op; обновление старой схемы с
работающим заданием на ревизии 617. UI-тесты покрывают открытие/закрытие,
успех, редактирование, no-op, конфликт и результаты refresh.

Браузерная проверка использует настоящий UI с локальными API-фикстурами:
320/360/390/430/1280 px и уменьшенную высоту viewport для клавиатуры.
Два сохранения прошли через существующий маршрут; ошибок консоли и неожиданных
запросов не было. Физическая клавиатура и Telegram WebView на устройстве не проверялись;
native Back покрыт тестом общего стека обработчиков. Live BGG и production-БД
в этой задаче не использовались.

Итоговая проверка 2026-09-16: `dotnet restore`, Release build (0 предупреждений),
Release tests с PostgreSQL 17 — 571/571, без пропусков; `npm ci`, `npm run check`,
frontend tests — 155/155 в 37 файлах; `npm run build` и Docker build — успешно. Frontend tests
повторены с `--maxWorkers=2`: при одновременной Docker-сборке исходный запуск
получил тайм-ауты старта шести процессов. Повтор прошёл без ошибок.
